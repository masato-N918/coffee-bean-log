# レビュー観点チェックリスト

SKILL.md の手順 3（コードレビュー）で使う、観点ごとの確認項目。
上から機械的に埋めるためのものではない。読んでいて気になった箇所について「この観点で見落としがないか」を確かめるために使う。
実際のチェックで見つかったパターンは、ここに追記していくとよい（同じ形の問題が別の場所にないかを見るのに役立つ）。

## 目次
1. バックエンド（FastAPI / SQLAlchemy 2 / Pydantic v2）
2. データベース（MySQL 8.4 / Alembic）
3. フロントエンド（Vue 3 / TypeScript / Pinia / Vue Router）
4. API の設計（フロントとバックの境界）
5. テスト・CI・開発環境

## 1. バックエンド（FastAPI / SQLAlchemy 2 / Pydantic v2）

**セッションとトランザクション**
- DB セッションを `Depends(get_db)` で受け取り、リクエストの終わりに必ず閉じているか（`yield` + `finally`）
- 1 つの操作で複数の書き込みをするとき、途中で失敗しても中途半端な状態が残らないか（commit は最後に 1 回か、例外時に rollback されるか）
- 「読んでから書く」処理（存在チェック → 更新）で、存在しない ID のときに 404 を返しているか
- `session.get()` / `select()` は SQLAlchemy 2.x の書き方になっているか（古い `session.query()` と混在していないか）

**入力検証（Pydantic）**
- スキーマの制約（`Field(max_length=...)`、`ge` / `le`、`Literal` / `Enum`）が、DB の制約（NOT NULL・VARCHAR 長・CHECK）と対応しているか
- 登録用と更新用でスキーマを分けている場合、片方だけ制約が抜けていないか
- 前後の空白の扱い（trim）や、空文字を `None` として扱うかが、登録と更新でそろっているか。空白だけの文字列が必須項目を通ってしまわないか
- 日付・数値の範囲（未来日を許すか、評価は 1〜5 か、量は正の数か）が要件どおりか
- レスポンスは `response_model` で型を決めているか（ORM オブジェクトをそのまま返して、余計な項目が出たり項目が欠けたりしないか）。`model_config = ConfigDict(from_attributes=True)` があるか

**例外とエラーレスポンス**
- エラーの形式がそろっているか：`HTTPException` の `detail`、入力不正時の 422（`RequestValidationError`）、想定外の 500。フロントがどの形式も扱えるか
- DB の制約違反（`IntegrityError`、外部キー違反）が 500 のまま返っていないか
- エラーメッセージが状況に合っているか（更新なのに「登録できませんでした」など）

**SQL・クエリ**
- 文字列連結で SQL を組み立てていないか（`text()` を使う場合もバインドパラメータを使う）
- `LIKE` / `contains()` 検索で、キーワード中の `%` と `_` をエスケープしているか（しないとワイルドカードとして効く）
- 一覧で関連データ（豆ごとの抽出記録など）を取るとき、N+1 になっていないか（`selectinload` / `joinedload`）
- 複数条件の絞り込みで、条件を指定しないときに全件、指定したときに AND になっているか

**構成**
- 動作確認用に一時的に作ったもの（ダミーのエンドポイント、print デバッグ）が残っていないか
- 設定値（DB の接続情報）が `pydantic-settings` 経由で `.env` から読まれ、コードに直書きされていないか
- 関数・ルーターの責務が大きくなりすぎていないか（目安として、ルーターの中に長い処理が増えてきたら `services/` や `crud/` に分ける）

## 2. データベース（MySQL 8.4 / Alembic）

- 適用済みのマイグレーションファイルを書き換えていないか（変更は `uv run alembic revision --autogenerate` で新しいリビジョンを作る）
- autogenerate が拾わない変更（CHECK 制約、型の細かい変更、サーバ側のデフォルト値）を、手で書き足しているか。`uv run alembic check` でモデルとの差分がないか
- `downgrade()` が `upgrade()` を正しく戻せるか
- `ORDER BY` の根拠になっている列が、本当に意図した順序を表しているか。同じ値（同じ日付・同じ評価）のときに順序が安定するよう、`id` などを第 2 キーにしているか
- 外部キーにインデックスがあるか、`ON DELETE` の挙動（豆の削除時に抽出記録も消す）が要件と合っているか。SQLAlchemy 側のリレーション（`cascade="all, delete-orphan"` / `passive_deletes=True`）と DB 側の設定が矛盾していないか
- 文字コードが `utf8mb4` か（絵文字や一部の漢字が入るため）
- `DATETIME` / `TIMESTAMP` とタイムゾーンの扱い（サーバの `TZ`、Python 側の naive / aware）がそろっているか
- 動作確認用のサンプルデータ（`backend/scripts/seed.py`）が、マイグレーションに混ざっていないか
- `created_at` / `updated_at` のような監査用の列があるか（必須ではないが一般的）

## 3. フロントエンド（Vue 3 / TypeScript / Pinia / Vue Router）

**状態の組み合わせ**（不具合が最も出やすい）
- 送信中に同じボタンを連打できないか（二重登録）、送信中に画面を離れたときに後から結果が反映されないか
- 同じコンポーネントのままルートパラメータだけ変わるとき（`/beans/1` → `/beans/2`、`/beans/new` ↔ `/beans/:id/edit`）、データを取り直しているか（`watch` で `props.id` を監視するか、`<RouterView :key="route.fullPath">`）
- 確認ダイアログを開いたまま、Esc や背景クリック、別の操作をしたときに、意図しない処理が走らないか
- エラーを表示した直後に、再取得の処理がエラーを消していないか。エラー時に画面全体が隠れてしまわないか
- 絞り込み・並び替えの状態が、画面を移動して戻ったときにどうなるか（Pinia に残す／URL のクエリに持つ、の方針が一貫しているか）
- フォームを編集途中で離れたときの扱い（警告を出すか）が要件と合っているか

**非同期処理**
- 絞り込みのように連続して呼ばれる処理で、古いレスポンスが新しい結果を上書きしないか（リクエストの番号を比べる、`AbortController` など）
- `await` の失敗を `try / catch` で受けて、ユーザーに見える形でエラーを表示しているか。読み込み中の表示があるか
- 削除や登録のあと、一覧や詳細を最新にしているか（Pinia のキャッシュが古いまま残らないか）

**構成・可読性**
- 1 つのファイルが大きくなりすぎていないか（目安として数百行を超えたら `components/` や composable に分ける）
- 同じエラー処理・同じ表示の変換（選択肢の値 → 表示名）が何度もコピーされていないか
- テンプレート由来で使っていないファイル（`src/assets/` の画像・CSS、`HelloWorld.vue` など）が残っていないか
- `v-for` に安定した `:key`（配列の index ではなく `id`）を付けているか。`v-if` と `v-for` を同じ要素に書いていないか

**アクセシビリティ**
- クリックできる要素が `<button>` / `<RouterLink>` になっているか（`div` に `@click` を付けるのではなく、本物の要素を使うのが基本）
- フォームの入力欄に `<label>` が結び付いているか、エラーメッセージが入力欄と関連付いているか
- 星評価のような独自の入力部品が、キーボードで操作でき、現在値が読み上げられるか
- ダイアログにフォーカス管理があるか。ネイティブの `<dialog>` 要素を使うと、Esc・フォーカス管理・背面の操作無効が標準でそろう
- `index.html` の `lang` と `<title>` がアプリに合っているか（Vite テンプレートのままだと `lang="en"`、`<title>Vite App</title>`）

**TypeScript**
- `as` による型の上書きが、実際のデータと合っているか（API のレスポンスを `as Bean` しているが、実際には一部のフィールドが返ってこない、など）
- `any` や `!`（非 null アサーション）で型エラーを黙らせていないか
- ルートパラメータ（文字列）を数値の ID として使うときに、変換と不正値の扱いがあるか

## 4. API の設計（フロントとバックの境界）

- `frontend/src/types/` と `backend/app/schemas/` の項目名・型・null の扱いが一致しているか（Python 側の `snake_case` をそのまま使っているか、変換しているか、が一貫しているか）
- 選択肢の保存値（焙煎度・抽出方法など）が、`docs/データ設計書.md`・`backend/app/models/choices.py`・`frontend/src/constants/choices.ts` でそろっているか
- 同じリソースなのに、エンドポイントによってレスポンスの形が違わないか（一覧と詳細で項目が違う場合、それが意図どおりで型にも表れているか）
- クエリパラメータの形式（複数選択を `?roast=a&roast=b` で送るか、カンマ区切りか）が両側で一致しているか
- HTTP メソッドとステータスコードの使い方（作成 201、削除 204、存在しない 404、入力不正 422/400）と、フロントの扱い（204 のときに JSON を読もうとしないか）
- 開発時のプロキシ（`vite.config.ts` の `/api`）と本番の配信構成で、パスがずれないか

## 5. テスト・CI・開発環境

- バックエンド：API のテスト（`TestClient`）が、正常系だけでなく 404・422・削除時の連動などをカバーしているか。DB が必要なテストと不要なテストが分かれているか
- フロントエンド：Vitest + `@vue/test-utils` で、入力チェック（`forms/`）や API ラッパー（`api/`）のような壊れても気付きにくいロジックにテストがあるか。テストのない画面・コンポーネントはどれか
- Python の型チェッカー（mypy / pyright）があるか。ruff の設定（`select`）が最小限すぎないか
- oxlint / ESLint の設定が最小限すぎないか（`suspicious` カテゴリや a11y 関連のルールを有効にしているか）
- CI（GitHub Actions）で、PR ごとに lint・型チェック・ビルド・テストが自動で走るか。PR ベースで運用しているなら、自動チェックがあるのが一般的（MySQL が必要なテストは `services:` で MySQL を立てる）
- `.editorconfig` がフロントだけでなくリポジトリ全体（Python・Markdown・YAML）をカバーしているか
- `.env` がコミットされていないか、`.env.example` が最新か
- Node.js / Python のバージョンが `.node-version`・`.python-version`・`package.json` の `engines`・`pyproject.toml` の `requires-python`・README でそろっているか

## 6. インフラ・デプロイ（Terraform / EC2 / RDS for MySQL / デプロイスクリプト）

`terraform/` を作ったあとに使う。

**Terraform**
- `required_version` とプロバイダの `version` が指定されているか。`.terraform.lock.hcl` がコミットされているか
- 環境ごとに変わる値（本人の IP など）が変数になっているか。必須の変数に `validation` があるか
- セキュリティグループのルールは、推奨の書き方（`aws_vpc_security_group_ingress_rule` などで 1 ルール 1 リソース）になっているか
- AMI を「最新」で取っている場合、`lifecycle { ignore_changes = [ami] }` がないと、新しい AMI が出るたびに apply でインスタンスが作り直される
- `user_data` を変えたときに反映されるか（`user_data_replace_on_change`）。作り直してよい設計（データを EC2 に置かない）になっているか
- EC2 の起動直後にインターネットを使う（dnf など）なら、ルートテーブルの関連付けができてから起動するよう依存関係があるか
- 使っていない変数・出力・データソースが残っていないか

**ネットワークとアクセス制御**
- `0.0.0.0/0` からの受信を許可しているルールがないか（HTTP を公開する場合は、要件として明記されているか。SSH は本人の IP のみ）
- RDS への接続元を IP（CIDR）ではなく、EC2 のセキュリティグループで指定しているか。ポートは 3306 だけか
- RDS が `publicly_accessible = false` で、インターネットへの経路がないサブネットに置かれているか
- IAM ポリシーが最小権限か（`Resource = "*"` になっていないか）
- EC2 のメタデータが IMDSv2 必須（`http_tokens = "required"`）になっているか、ディスクと RDS が暗号化されているか

**秘密情報**
- DB のパスワードが tf ファイル・tfvars・user_data に平文で書かれていないか（`random_password` + SSM パラメータストア / Secrets Manager が一般的）
- state にはパスワードが平文で残る。state を Git に入れていないか、ドキュメントでその注意を書いているか
- サーバー上に `.env` などを作る場合、権限が本人だけ（600）になっているか
- パスワードに記号を使う場合、受け取る側（`DATABASE_URL` の URL エンコード、シェル、`.env`）で特別な意味にならないか

**user_data（EC2 の初回セットアップ）**
- `set -euxo pipefail` で途中の失敗に気付けるか
- `templatefile` で読み込むため、シェルの `${VAR}` が Terraform の変数展開と衝突していないか（`$${VAR}` にするか `$VAR` と書く）
- パッケージ名・バージョンが実在するか（Amazon Linux 2023 の Python・Node.js のパッケージ名、uv の導入方法）
- 改行コードが LF に固定されているか（`.gitattributes` の `*.tftpl text eol=lf`）
- アプリ（uvicorn / FastAPI）を systemd で動かす場合、異常終了時の再起動（`Restart=on-failure`）、`.env` の読み込み（`EnvironmentFile`）、起動前のマイグレーション（`alembic upgrade head`）の順序を考慮しているか
- フロントのビルド成果物を nginx などで配信し、`/api` をアプリに転送する設定と、Vue Router の履歴モード用のフォールバック（`try_files ... /index.html`）があるか

**デプロイスクリプト（PowerShell）**
- UTF-8 BOM 付きで保存されているか（Windows PowerShell 5.1 は BOM なしの UTF-8 を Shift_JIS として読む）
- 外部コマンドの失敗を `$LASTEXITCODE` で判定しているか
- PowerShell 5.1 から ssh にコマンドを渡すと、二重引用符が崩れる。リモートのコマンドに二重引用符を使っていないか
- Windows の `scp -r` で送ったディレクトリは権限が 700 になり、nginx などの別ユーザーが読めない（403）。配置後に `chmod` で権限をそろえているか
- 途中で失敗したとき、中途半端な状態（新しい API と古い画面の組み合わせなど）が残らないか
- 未コミットの変更がそのままデプロイされないよう、チェックがあるか
- 起動の確認（`/api/health` へのヘルスチェック）をしてから「完了」と表示しているか

**ドキュメント**
- 構成図・リソース一覧に、実際の tf と食い違いがないか
- 手順に書いたコマンドがそのまま動くか（ディレクトリの移動、ファイル名）
- 費用の目安と、使い終わったら `terraform destroy` で削除する手順が書かれているか
